# Ergänzung 0.1.5: Standardhost

Ein ausdrücklich ausgewählter Standardhost darf innerhalb der Plugin-Konfiguration DefaultServer on erhalten. Die Hauptserver-/Fremdhost-Sperren gelten unverändert. DefaultServer ersetzt keine nachgewiesene Namensauswahl bei schon passenden Alt-VirtualHosts derselben IP. Auswahl, Lifecycle, Erstaktivierung und Rücknahme: [DEFAULT-HOST.md](DEFAULT-HOST.md).

# Dokumentierte Einschränkungen — 0.1.3

- Beta. Kein vollständiger Debian-12-/Virtualmin-8.3-/ProFTPD-1.3.8-Integrationstest, kein echter Listener, keine geprüfte Anmeldung, kein bewiesener störungsfreier Reload bestehender Sitzungen. Automatisierte Tests ersetzen das nicht.
- Exakte Versionsfreigabe: Virtualmin `8.3.0.gpl`; ProFTPD-Familie `1.3.8`; Debian 12. Die Perl-Anbindung prüft Virtualmins Version bei jedem Aufruf. Nach einem Update muss das Plugin eingefroren und erneut geprüft werden. Alte Konfiguration verschwindet bei einem Update nicht automatisch.
- Bei versionierten Webmin-Verzeichnissen muss das Modul unter dem aktuell in `/etc/webmin/miniserv.conf` eingetragenen Root liegen. Die Laufzeitanbindung verweigert Arbeit aus einem alten Root; ein Timer darf nach einem Webmin-Wechsel nicht still alte Bibliotheken weiterbenutzen. Neuer Installationsort und Servicepfad benötigen einen geprüften Abgleich.
- Nur eigenständiger ProFTPD-Dienst unter `proftpd.service`, explizites FTPS auf 21. Kein inetd, kein implizites FTPS auf 990, kein SFTP, kein alternativer Dienstname.
- Statischer, konservativer Include-Scanner: absolute Dateipfade/Globs, keine Includes von Verzeichnissen, keine Zeilenfortsetzungen, keine Variablenauswertung. Bedingungen wie IfModule werden beim Konfliktscan konservativ berücksichtigt, auch wenn sie zur Laufzeit inaktiv wären. Das kann sichere Konfigurationen vorsorglich ablehnen. Fremde globale IgnoreSNI-/UseImplicitSSL-Optionen werden nicht automatisch geändert.
- Kein vollständiger ProFTPD-Semantikparser. Erst der echte Syntaxcheck und Handshake auf dem Zielsystem beurteilen die reale Konfiguration. Globale Authentifizierungs-, Limit-, NAT- und Modul-Einstellungen können das Verhalten beeinflussen.
- Auf Shared-IP-Systemen ist korrekte Client-Auswahl des Domain-Hosts erforderlich. Ohne SNI bzw. geeignetes HOST ist ein individuelles Zertifikat nicht zugesichert. FTP-Benutzername ist kein Ersatz für Zertifikatsauswahl vor der Anmeldung.
- Keine Migration existierender VirtualHosts, keine automatische Erzeugung zusätzlicher FTP-DNS-Namen. Das Zertifikat muss den eigentlichen Domainnamen abdecken; `ftp.domain` wird nicht still als Alias hinzugefügt.
- Domain-Aliase ausgeschlossen. Echte Top-Level-/Subserver benötigen Home, Gruppe und Website-SSL. Eine Gruppe kann mehrere Subserver abdecken; keine zusätzliche Isolation innerhalb einer gemeinsam verwendeten Unix-Gruppe. Benutzerkonten/Shell-Freigaben/PAM werden nicht verändert. Vorhandene ProFTPD-Anmelderegeln müssen weiterhin passen.
- Checkbox und Menü stammen aus der Feature-API. Das Prüfmenü ist Hauptadministratoren vorbehalten; keine automatische Freigabe des Moduls an Domain-Eigentümer/Reseller. Das UI ist eine einfache Prüfseite, kein Editor für beliebige ProFTPD-Direktiven.
- Der Hauptserver muss für diesen Modus mit `Port 0` und `DefaultServer off` deaktiviert sein. `TLSEngine off` im Hauptserver ist dann kein Aktivierungsfehler. Bestehende Alt-Hosts müssen vor dem Umschalten hinsichtlich ihres eigenen Ports geprüft werden. Ein Kaltstart ganz ohne aktiven VirtualHost und das Entfernen des allerletzten Hosts brauchen einen gesonderten Diensttest; die Kombination mit `proftpd.service` ist hier nicht praktisch abgenommen.
- Ein Domainbanner ist vor Namensauswahl auf geteilter IP nicht garantiert. HOST kann eine neue Begrüßung auslösen; SNI ändert eine schon gesendete Begrüßung nicht rückwirkend. Kein Versprechen einer generellen Abweisung von IP-Verbindungen oder Clients ohne Namensauswahl.
- Temporäres Disable erzeugt einen DenyAll-Loginbereich, statt den Host zu entfernen. Bereits bestehende Sitzungen werden nicht gezielt beendet. Delete entfernt nur den eigenen Host. Dadurch werden globale FTP-Zugänge über den Hauptserver oder andere fremde Hosts nicht automatisch gesperrt; das Plugin ist keine systemweite FTP-Kontosperre.
- Kein separater Backup-/Restore-Hook für Virtualmin-Domain-Backups. Domain-Zustand kann beim nächsten Timerlauf neu generiert werden, sofern das Feature-Flag und gültige Website-Zertifikate wiederhergestellt wurden. Plugin-Konfiguration und Journal sind zusätzlich zu sichern. Website-Zertifikate gehören zum Website-Backup; bereits vorhandene Snapshots aus Versionen bis 0.1.6 bleiben für eine Migrationsrücknahme bestehen.
- Keine vorzeitige OCSP-/CRL-Sperrprüfung. Der Debian-CA-Speicher muss aktuell sein. Keine verschlüsselten Schlüssel; Ed25519/DSA-Serverzertifikate ausgeschlossen. Neue unvollständige Zertifikate können pending sein; der Wartezustand muss überwacht werden.
- Eine aktive Domain mit defektem neuen Zertifikat blockiert die vollständige Timer-Transaktion. Nach Behebung wird erneut versucht. Alte Konfiguration bleibt bestehen; das ist kein Schutz vor dem Ablauf alter Zertifikate.
- Verzögerung: ungefähr 60 Sekunden nach Ende des letzten Laufs, zuzüglich Laufzeit und systemd-Planung. Nach tatsächlichen Lifecycle-Änderungen gilt zusätzlich eine 120-Sekunden-Schonfrist für das Speichern der Domain-Daten. Das ist keine globale Transaktion mit Virtualmin; sehr lange oder fehlgeschlagene Kernoperationen müssen gesondert beurteilt werden. Service-Timeout 300 Sekunden. Keine sofortige Zertifikats-Renewal-Garantie. Große Domainzahlen erfordern Lastmessung und gegebenenfalls spätere Optimierung.
- Kern-Dateisperren und Plugin-Sperren koordinieren unterstützte Verwaltungswege. Es gibt keine Garantie gegen gleichzeitige manuelle Eingriffe durch andere Root-Werkzeuge. Wartungsbefehle benötigen ein ruhiges Konfigurationsfenster.
- Rollback stellt nur Plugin-Konfiguration/Zustand zurück, nicht gelöschte Domains, Benutzer, IPs, Firewallregeln oder globale ProFTPD-Einstellungen. Rollback/Freeze/Deaktivierung stoppen Automatisierung; Wiederaufnahme ist absichtlich ein manueller, abgestimmter Wartungsschritt.
- Keine automatische Bereinigung: alte Zertifikatsgenerationen aus Versionen bis 0.1.6 können bestehen bleiben; ab 0.1.7 werden keine neuen erzeugt. Sie sind privat, enthalten Schlüssel und benötigen eine festgelegte Aufbewahrung. Keine automatische Paketaktualisierung oder Neuinstallation über vorhandene Zustandsdaten.
- Die passiven Ports sind in 0.1.3 auf den mitgelieferten Bereich abgestimmt. Eine nachträgliche direkte Änderung der JSON-Konfiguration kann als Konfigurationsabweichung erkannt werden und braucht einen geplanten Abgleich; die Datei ist kein allgemeines Live-Einstellungsformular.
